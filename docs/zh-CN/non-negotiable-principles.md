# 灵珑不会妥协的十条原则

本文档不是功能清单，  
也不是普通编码规范。

它回答的是一件更根本的事：

> **什么东西一旦让步，灵珑就会开始不再是灵珑。**

因此，这十条原则不是“最好如此”，  
而是灵珑在长期演进中必须反复回来的锚点。

---

## 一、使用方式

这十条原则用于 4 类场景：

- 架构设计取舍
- 大规模重构前的方向校准
- PR / 评审时的高层裁决
- 当团队出现分歧时的最终回锚

如果某个方案技术上成立，  
但违反了其中任意一条，就不应被视为真正符合灵珑方向。

---

## 二、十条原则

### 1. 为人服务，高于技术完美

灵珑的最高原则，不是技术炫技，不是架构洁癖，  
而是**为人服务，且是长期地为人服务**。

这意味着：

- 不能为了“更高级”牺牲人的理解与信心
- 不能为了“更纯粹”牺牲维护体验与协作成本
- 不能让系统在形式上更强，却让人更不敢接近

不接受的退化信号：

- 为了理论优雅，显著增加理解门槛
- 为了架构统一，牺牲维护者的现实体验
- 让系统变成只有少数人才能碰的黑箱

---

### 2. 通过架构维持秩序，而不是制造控制

灵珑的架构目标不是压迫变化，  
而是让变化在有秩序的前提下发生。

秩序的意义在于：

- 让系统不靠运气运行
- 让问题不靠猜测定位
- 让人可以在理解影响的前提下继续修改

不接受的退化信号：

- 用更多控制点制造更重的系统负担
- 用不可解释的中间层替代清晰的边界
- 让治理能力变成新的混乱来源

---

### 3. 边界先于灵活性

灵珑可以接受克制的动态能力，  
但不接受以破坏边界为代价换来的伪灵活性。

优先级始终是：

1. 边界清楚
2. 权限清楚
3. 归属清楚
4. 再讨论灵活性

不接受的退化信号：

- 默认兜底放过
- 隐式穿透边界
- 让共享层承担实现细节
- 把方便放在边界清晰之前

---

### 4. 单一真源与唯一写入口不可被破坏

灵珑不接受“谁都能改一点”的系统。  
事实状态、写权限、编排权必须有清晰归属。

这条原则在运行时里的直接体现是：

- 状态机必须有唯一写入口
- 聚合对象不能反向扩散写权限
- 编排层不能绕过协调器直接改状态

不接受的退化信号：

- 第二份事实状态
- 对象之间互相拿着对方乱改
- 为了兼容重新开放已收敛的旧写入口

---

### 5. 复杂性不能消失，但必须归位

灵珑不相信复杂性会凭空消失。  
它只要求复杂性待在该待的位置上。

因此：

- 必要复杂性可以接受
- 偷懒型复杂性不接受
- 复杂性必须被边界包住，不能四处蔓延

不接受的退化信号：

- 字符串魔法键四处扩散
- Spring / JVM 深水补丁到处散开
- Map / 附件表替代清晰的状态与语义对象

---

### 6. 运行时治理优先于部署叙事

灵珑不是用“部署形态升级”掩盖治理问题。  
它首先关心的是进程内是否能隔离、定位、回收、恢复。

因此：

- 先问运行时语义是否成立
- 再问外部形态是否需要变化
- 先学会治理，再讨论扩散

不接受的退化信号：

- 一遇到复杂度就本能转向拆分叙事
- 用外部系统替代本该在进程内成立的治理语义
- 把内部边界问题伪装成部署方案问题

---

### 7. 长期运行优先于瞬时成功

灵珑默认系统会运行很久，  
所以任何设计都不能只看“刚启动时能不能跑”。

必须优先考虑：

- 内存如何老化
- 资源如何积累
- 状态如何腐化
- 重启为何不可预测

不接受的退化信号：

- 只验证一次成功路径
- 只看短时间内是否可用
- 不考虑卸载、回收、长期退化

---

### 8. Shared API 必须极度克制

`Shared API` 在灵珑里不是普通依赖，  
而是进入共享边界后的进程级公共契约。

因此：

- 必须由真实消费者驱动契约
- 只允许增量兼容演进
- 已加载 Shared API 不允许热更新、不允许热卸载
- 涉及更新必须通过进程重启生效

不接受的退化信号：

- 为了方便把实现类塞进 Shared API
- 破坏契约仍想靠热更兜住
- 共享层职责不断膨胀

---

### 9. 每一次演进都必须可解释、可验证、可回退

灵珑不接受“理论上应该没问题”的演进方式。  
任何重要改动都必须能解释、能验证、能收敛。

至少要回答：

- 为什么这么改
- 谁的边界被影响
- 如何验证没有破坏语义
- 如果失败，怎么回退或收敛

不接受的退化信号：

- 只改代码，不补测试与文档
- 改完以后说不清语义变化
- 只能前进，无法收敛

---

### 10. 保持温度，保护维护者的信心与成就感

灵珑最终不是冷冰冰的治理机器，  
而是一套让人愿意继续建设的工程体系。

因此：

- 文档要帮助人理解，而不是堆概念
- 日志要帮助人定位，而不是制造恐慌
- 错误信息要帮助人行动，而不是羞辱人
- 代码要让接手者感到被尊重，而不是被排斥

不接受的退化信号：

- 为了整洁删掉高价值设计注释
- 为了统一风格抹平经验与踩坑说明
- 让系统越来越冷、越来越硬、越来越难靠近

---

## 三、如何用这十条原则裁决方案

当你面对一个架构方案时，至少问自己 5 个问题：

1. 它有没有更好地为人服务，而不是只满足技术完美？
2. 它有没有让边界更清楚，而不是更模糊？
3. 它有没有让写权限和事实状态更集中，而不是更分散？
4. 它有没有让长期运行更可证明，而不是只让短期实现更漂亮？
5. 它有没有让维护者更敢改、更能解释、更有信心？

只要其中有 2 个问题回答不出，  
这个方案通常就不该继续推进。

---

## 四、最后的收敛结论

灵珑不会妥协的，不是某一项具体技术实现，  
而是这套持续成立的内核：

> **通过架构维持秩序，将自由、信心、温度与成就感归还给人。**

这十条原则存在的意义，  
就是确保灵珑在未来无论再重构多少次，  
依然不会失去她之所以是灵珑的原因。
